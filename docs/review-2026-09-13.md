基準日: 2026-09-13  
対象: [設計](./design.md)、[ADR](./adr.md)、`tools/` 配下のスケッチ  
状態: 第1回・第2回とも設計へ反映済み（実機採取・実測は作業待ち）

## 確認済み事項

- 7.2のテストベクトル4件を7.1の規則から手計算で再現し、チェックサム含め全件一致した
- byte 6（モード）と byte 8 の値は IRremoteESP8266 の `IRMitsubishiAC::setMode` 実装と一致する
- design.md と adr.md の間に矛盾はない
- 全体の割り切り（ESP32を接続維持と36文字送信だけに絞り、状態・時刻・変換をクラウドとアプリへ寄せる）は判断原則に忠実である
- Alarm handler の「削除してから送る」順序は二重送信防止として正しい

## 要修正（実装前に決めるべきこと）

### R-1. 「接続中」の判定が弱く、503 と 202 の区別が障害判断表ほど信頼できない

対象: design.md §5.5、§9

ESP32 が突然電源断すると、Durable Object 側の socket は TCP タイムアウトまで open に見え、`send()` は成功して 202 を返す。protocol ping は runtime が処理して DO に届かず、ESP32 からのアプリ用メッセージも無いため、DO は ESP32 の生存を一切知らない。ESP32 が復帰して再接続すれば置き換わるが、それまで「202 だが動かない」が続く。

対策案（いずれかを選ぶ）:

- 現状維持: §9 の表に「202 でも接続が死んでいる場合がある。ESP32 が再接続すれば解消する」と注記する
- 生存確認を追加: ESP32 が30秒ごとにテキスト `PING` を送り、DO は `ctx.setWebSocketAutoResponse` で `PONG` を自動返答する（DO は起きない）。`POST /command` で `ctx.getWebSocketAutoResponseTimestamp(ws)` が90秒以上古ければ 503 を返す。ESP32 側は `PONG` を4文字の不正入力として捨てるだけでよく、パーサーは不要。ADR-010 の「応答なし」を一部緩めるため、採用する場合は ADR に記録する

### R-2. `PUT /schedule` の `executeAt` 検証が未定義

対象: design.md §5.2、§5.5

過去時刻、パース不能な文字列、遠すぎる未来の扱いが書かれていない。`storage.setAlarm()` へ過去時刻を渡すと即時発火し、意図しない即時送信になる。

対策: 「現在以前、またはパース不能なら 400」を §5.5 に明記する。上限（例: 7日以内）を設けるかも決める。

### R-3. テストベクトルのうち実機採取と分かるのは1件だけ

対象: design.md §7.2

1件目（ON / dry / 24℃ / auto / middle）は `ir_loopback_test.ino` の配列と同じで採取値と推測できる。2〜4件目は仕様から導出したものであり、エンコーダが仕様に一致することしか保証しない。

実リモコンから採取して照合すべき項目:

- `quiet=5`。IRremoteESP8266 では 5 は `kMitsubishiAcFanMax`（送信時に 4 へ丸める）、6 が `kMitsubishiAcFanSilent` として扱われる。実機の静音がどの値かは採取で確定させる
- heat / 風量4 / low の組み合わせ
- byte 10〜16 の固定部。三菱のリモコンは時計やタイマーをこの領域に含める機種があり、採取値がゼロでない場合は固定部の妥当性を再確認する

### R-4. CA bundle の出自と Cloudflare 側 CA のローテーション

対象: design.md §4.6、§9

bundle をどう生成して埋め込むかが未記載。Cloudflare のエッジ証明書は発行元が変わることがある（Google Trust Services、Let's Encrypt、SSL.com など）。狭い bundle だと予告なく TLS 失敗の30秒ループに入り、復旧は USB になる。

対策:

- Mozilla のフル bundle（約65KB。Flash に余裕あり）を使うと §4.6 に明記する
- bundle の生成手順（arduino-esp32 の `gen_crt_bundle.py` 等）と埋め込み方法を記載する
- §9 の表に「Wi-Fi 成功・ws 失敗が続く = 証明書 / bundle の疑い」を加える

### R-5. arduinoWebSockets のバージョン未固定と自動再接続の抑止

対象: design.md §4.5、§4.7

- §4.7 に arduinoWebSockets の版がない。`beginSslWithBundle()` の size 引数は比較的新しい API なので版を固定する
- ライブラリ自身に自動再接続（`setReconnectInterval` 既定 500ms）があり、firmware 主導の30秒方針と競合する。TEARDOWN で `disconnect()` し、OFF_WAIT 中は `loop()` を呼ばないことで抑止する意図を §4.5 に明記する

## 追記推奨（小さいが未定義）

### A-1. APP_TOKEN の保管と投入方法

対象: design.md §6

Keychain に保存し、UserDefaults を使わないことを明記する。投入方法（ビルド時定数か設定画面か）も決める。Worker 側の Bearer 比較は `crypto.subtle.timingSafeEqual` を使う。

### A-2. `GET /schedule` の応答形式

対象: design.md §5.5

`payload` を返すかどうかが未定義。ログ方針（payload を記録しない）と揃えるなら返さない。

### A-3. 発火済みとキャンセル済みの区別

対象: design.md §5.2、§6

`GET /schedule` が `null` を返した時、発火済みかキャンセル済みかを区別できない。許容するなら明記する。

### A-4. TLS 中の Task WDT

対象: design.md §10

TLS handshake の最大120秒ブロックの大半は socket 待ちで idle タスクが走るため、`enableCore1WDT()` は発火しないはず。ただし実測項目に「TLS 接続中に WDT が発火しない」を加える。

### A-5. Base 抵抗 220Ω

対象: design.md §8.2

Ib は約11.8mA で、ESP32 GPIO の推奨上限 12mA 付近。S8050 の hFE 最小 85 で Ic 108mA なら数 mA で飽和するため、330〜470Ω でも動く。実測方針なので任意。

### A-6. GPIO15 はストラッピングピン

対象: design.md §8.1

GPIO15 は起動時のログ出力抑制に使われる。受信モジュール出力はアイドル HIGH なので問題ないが、解析時のみ接続する旨をピン表へ注記する。

## 第2回レビュー（第1回反映後）

### 一次情報で確認した事実

- arduinoWebSockets 2.7.2 は存在する（2025-12-20 公開の最新タグ）
- `beginSslWithBundle(host, port, url, CA_bundle, CA_bundle_size, protocol)` は arduino-esp32 3.0.4 以降向けの宣言として存在する
- arduino-esp32 3.3.11 の `NetworkClientSecure::setCACertBundle` は bundle が null または size 0 の場合に `esp_crt_bundle_detach` を呼び検証を外す。design.md の「null は検証なし接続」は正確
- arduino-esp32 3.3.11 の `tools/` に `gen_crt_bundle.py` が存在する
- WebSocketsClient の `_reconnectInterval` 既定値は 500ms。`loop()` は未接続かつ `millis() - _lastConnectionFail >= _reconnectInterval` のとき再接続を試みる

### 第1回指摘の反映確認

R-1 は「限界を明記して現状維持」で妥当。§5.5、§9、ADR-010、ADR-018 の記述は整合している。R-2、R-4、A-1〜A-4、A-6、T-1 は設計へ正しく反映されている。R-3 は導出と採取の区別が付き、§11 の段階2にゲートとして入っている。

### R2-1. `setReconnectInterval(500)` が ADR-017 の試算と矛盾する（要修正）

対象: design.md §4.5、adr.md ADR-014、ADR-017

CONNECTING の15秒間に 500ms 間隔の内部再試行を許すと、失敗が速いケース（DEVICE_TOKEN 不一致で 401、DNS 失敗、TCP 拒否）では1サイクルで十数回から数十回の TLS handshake が走る。ADR-017 の「最大約2,880回/日」は1サイクル1回の前提で、実際は一桁多くなりうる。heap 断片化のリスクも増える。

対策: `setReconnectInterval` を CONNECTING の15秒より長い値にし、1サイクルの接続試行を1回にする。「失敗したら毎回30秒待つ」という ADR-017 の1規則と整合し、所有者が覚える分岐も減る。500ms を明示する理由がなければ撤回する。

### R2-2. iOS 側の `executeAt` 生成形式が未記載（追記推奨）

対象: design.md §6

§5.2 は `YYYY-MM-DDTHH:mm:ssZ` だけを受理する。Swift の `ISO8601DateFormatter` 既定（`withInternetDateTime`）はこの形式を出すが、`.withFractionalSeconds` を付けると 400 になる。§6 に「小数秒なし、UTC の `Z` で送る」を一行加える。

### R2-3. ADR-006 の GPIO 電流の根拠値（軽微）

対象: adr.md ADR-006

「約40mA」は最大駆動強度（3）の値で、`pinMode` 既定の駆動強度2では約20mA。11.8mA は依然下回るので結論は変わらないが、根拠の数字を直す。

### R2-4. ADR-014 の参考リンクが ESP-IDF v5.2（軽微）

対象: adr.md ADR-014

core 3.3.11 は IDF 5.5 系。bundle の形式は IDF 版で変わりうるため、同梱の `gen_crt_bundle.py` で生成する方針（§4.6）が正しい。リンクだけ 5.5 系のドキュメントへ差し替える。

### R2-5. §7.2 の静音採取の文言（軽微）

対象: design.md §7.2

「fan値が5になることを確認する」は結論を先取りしている。次段落で「異なれば規則を直す」とあるので実害はないが、「fan値を採取し、規則の5と一致するか照合する」に言い換えると意図が明確になる。

### R2-6. `ir_loopback_test.ino` のコメント（軽微）

対象: `tools/ir_loopback_test/ir_loopback_test.ino`

「電源ON / ドライ / 24℃ / 風量自動」に風向 middle が抜けている。§7.2 の1件目と同一配列であることを示すため揃える。
